# HTML Report

Produce a readable decision artifact, not a prescribed sequence of cards. Ask about audience, question, and scope if they affect the conclusion; otherwise state assumptions. Investigate first: link claims to primary evidence (file/line, measured result, or source URL), distinguish observation from inference, and identify material gaps. Compare distinct options when there is a real choice. Make a recommendation with reasons, trade-offs, and uncertainty. Choose headings and visual forms to suit the question; a useful starting arc is question → findings → implications/options → recommendation. Diagrams, tables, and before/after views earn their place by making a relationship easier to understand than prose would.

## Build

1. Read the current design-system `README.md`, `docs/foundations.md`, and `docs/components.md` at the supplied source path before composing. Require the source repository/package to contain `tokens/tokens.css` and `styles/snarfum.css`. Ask for its path if unavailable; the helper does not ship a fallback theme.
2. Author a complete UTF-8 HTML document in a temporary working directory (`mktemp -d` or the platform's equivalent), with `<html lang="en" class="dark">`, a descriptive `<title>`, `<meta name="viewport" content="width=device-width, initial-scale=1">`, a first-focusable `<a class="sn-skip-link" href="#main">`, and `<main id="main">`. Put `<!-- SNARFUM_STYLES -->` once in the head, after metadata. Use semantic headings and landmarks. Use `.sn-container`, `.sn-section`, `.sn-prose`, `.sn-card`, `.sn-tag`, etc. where appropriate; report-specific CSS should be small, scoped under `.report`, and use semantic tokens (`var(--border)`, `var(--foreground)`, `var(--space-*)`) rather than hardcoded palette or spacing. Follow the design system's title-case headings and mono labels. Set dark as the default; the same markup must work with `class="light"` on `<html>`.
3. Escape untrusted text and attribute values when assembling markup (`html.escape(value, quote=True)` in Python); validate link protocols (`https:`, `http:`, `mailto:`, or intentional local `#` anchors) and avoid injecting untrusted HTML, CSS, SVG, or script. Give visuals text labels/captions and explain what they prove; status needs a word, not just a hue. Reserve `--signal` for focus/selection/current navigation. Keep the body usable without scripts, remote fonts, CDNs, or other network assets; optional font links may enhance typography but system font fallbacks must remain readable offline. Use captions and labeled axes for charts, table headers for comparisons, responsive stacking/scrolling for wide content, visible focus, and legible contrast in both themes.
4. Run `python3 scripts/embed_css.py --design-system /path/to/design-system < draft.html` from this skill directory (or set `SNARFUM_DESIGN_SYSTEM` instead of the flag). The command prints the absolute path of a fresh single-file `.html` in the OS temp directory. It embeds the **current** token and component CSS, not a maintained copy. If it fails, resolve the missing dependency rather than substituting colors. Leave the draft and final report in temp; tell the user the final path without opening or publishing it unless explicitly requested.
5. Inspect the rendered document and its links at desktop/mobile widths and in dark/light modes when browser access is available; otherwise say visual/browser review was not performed. Check content accuracy and accessible structure separately from CSS/markup checks. Remove broken references and ensure offline viewing preserves layout.

The source of the design system remains its own repository; update reports by regenerating them from that source. Upstream inspiration and local adaptation are recorded in [SOURCES.md](../../SOURCES.md).
