# Live Pi handoff smoke test: 2026-10-31

## Scope and environment

The user explicitly authorized the live test after reviewing the proposed disposable-repository scenarios. This tested the real Pi TUI, extension loader, model inference, native session replacement, and approval dialogs—not a mocked runtime. The test controller selected Yes/No/Escape only for the harmless fixture task described below.

- Local macOS host; Pi **1.4.0**, also the latest published release when checked; tmux **3.7c** on a dedicated test-only socket.
- Selected provider/model/reasoning: **openai / gpt-6-astra / low**, using existing authentication without copying credentials.
- Configured defaults were **openai / gpt-6.1-sol / high**, so retaining the selection exercised non-default settings.
- Two disposable Git repositories, private session directories, and a private `XDG_STATE_HOME` beneath a temporary test root (shown below as `<private-test-root>`).
- Explicit one-invocation `--extension` loading. Discovered extensions, MCP, skills, prompt templates, themes, and context-file discovery were disabled; project instructions were read explicitly. `--no-approve` ignored trust-gated project configuration. No persistent agent enablement or global configuration changes were requested or made.
- `--offline` disabled automatic catalog/version activity, not the explicitly requested model inference. `--session-dir` kept all test sessions outside the normal session store.

The fixture task was to replace `result.txt` with `APPROVED-BLUE-37` plus a newline, read it back, and stop. `unrelated.txt` had to remain unchanged. `PLAN.md` held the authoritative task and pointed to an optional API document that was irrelevant to the task. A source-only diagnostic marker checked that conversation history was not copied into the receiver.

## Historical findings

1. **Delivery bookkeeping is delayed until the receiver turn finishes.** While the receiver was visibly processing the prompt and awaiting approval, its record still said `created`. In the uninterrupted run it became `delivered` after the turn ended. After the crash and successful recovery, it remained `created` because the original callback no longer existed. This conservatively avoids false success and did not create a duplicate, but status/recovery UX should distinguish prompt submission from turn completion and explain recovered sessions.
2. **The question can be repeated.** One proposal put “Proceed?” inside its verification field; the adapter added its own question, yielding two. Make the field contract explicit or normalize the displayed question without changing the proposed scope.
3. **Recovery instructions could state the evidence reset more explicitly.** The resumed agent initially reused its earlier brief read and received a gate error before rereading. Enforcement worked, but an explicit “reread the complete brief after resume/reload” startup instruction would avoid this extra round trip.

No approval bypass or unintended task mutation was observed. These are findings, not fixes applied by this test.

### Follow-up

Commit `c5d9682` subsequently addressed all three findings: receiver-side submission/settlement bookkeeping and history-based record repair, rejection of duplicate approval questions, and explicit reread/reinspection requirements after restoration. It also added separately confirmed local read grants. The current [adapter documentation](../../../vendor/pi/extensions/session-handoff/README.md) describes those behaviors, with offline regression coverage. The live results above apply only to the source hashes below; they do **not** establish live verification of the follow-up changes.

Private artifacts were retained outside this repository under `<private-test-root>` (the host-specific location is omitted from this public report):

- `evidence/summary.json`: machine-checked session IDs, settings, tool sequences, gate transitions, read paths, and final fixture contents.
- `evidence/01-proposal.txt` through `evidence/10-recovery-cancelled.txt`: captured rendered TUI states.
